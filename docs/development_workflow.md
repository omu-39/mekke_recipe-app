# レシピアプリ 開発フロー運用ガイド（個人開発／チーム開発準備）

> 本ドキュメントは、個人開発でありながら将来的なチーム開発への移行を見据え、
> `recipe_app_spec_v2.md`（仕様書）・`use_cases.md`（ユースケース一覧）・`naming_conventions.md`（命名規則）
> と連携して運用するための開発フローをまとめたものです。

---

## 1. 全体像

```text
Issue起票（UCベース）
    ↓
ブランチ作成（GitHub Flow）
    ↓
実装
    ↓
セルフレビュー（チェックリスト）
    ↓
CI（Lint・型チェック・テスト）
    ↓
PRマージ（mainへ）
    ↓
仕様書・ADR更新（必要な場合）
```

---

## 2. Issue管理

### 2.1 基本方針

- 思いついたタスクをすぐコードに落とさず、まず GitHub Issue に起票する
- 1 Issue = 1 PR を原則とし、大きすぎるタスクは分割する
- `use_cases.md` のユースケース番号（例：`UC-04-01`）を必ず紐づける

### 2.2 Issueテンプレート例

```markdown
## 対象ユースケース
UC-04-01：所持食材又はレシピ名でのレシピ検索

## 背景
（なぜこの実装が必要か）

## やること
- [ ] 所持食材の複数選択UIを実装する
- [ ] 検索APIを叩いて結果を分類表示する

## 完了条件（Definition of Done）
- [ ] 不足材料0/1/複数の3分類が正しく表示される
- [ ] ③カテゴリが不足数の昇順で並ぶ
- [ ] 検索結果0件時に代替表示が出る（5.6節）
- [ ] セルフレビューチェックリストを満たしている
```

### 2.3 タスクボード

GitHub Projects（または Notion 等）で以下の5列を用意し、Issueを流す。

| Backlog | Todo | In Progress | Review | Done |
|---|---|---|---|---|
| 未着手の全Issue | 次に着手予定 | 作業中 | セルフレビュー・CI待ち | マージ済み |

## 3. マイルストーン（スプリント）計画

1〜2週間単位で区切り、継続しやすくする。`use_cases.md` のカテゴリ単位を目安にする。

| マイルストーン | 対象ユースケース | 内容 |
|---|---|---|
| M1 | UC-01, UC-02 | 認証・アカウント管理、プロフィール管理 |
| M2 | UC-03, UC-04, UC-05 | 食材管理、レシピ検索、レシピ閲覧 |
| M3 | UC-06, UC-07 | レシピ投稿・編集・削除、お気に入り管理 |
| M4 | UC-08, UC-09 | 買い物リスト管理、レビュー・コメント |

各マイルストーン終了時に、簡単な振り返り（KPT等）を行うことを推奨する。

## 4. ブランチ運用（GitHub Flow）

### 4.1 原則

- `main` は常にデプロイ可能な状態を保つ
- `main` に直接コミットしない
- 作業は必ずブランチを切り、PR経由でマージする

### 4.2 ブランチ命名・コミットメッセージ

命名規則は `naming_conventions.md` 5.1節（ブランチ名）・5.2節（コミットメッセージ）に準拠する。個別の例はそちらを参照。

## 5. セルフレビュー（PRマージ前チェック）

一人開発ではレビューが省略されがちなため、**PR作成からマージまでに間を空ける**か、
以下のチェックリストで自己レビューしてからマージする。

### 5.1 仕様との整合性

- [ ] 該当UC番号の完了条件（Definition of Done）を満たしているか
- [ ] `naming_conventions.md` の命名規則に沿っているか
- [ ] 仕様書（`recipe_app_spec_v2.md`）の記載と実装に矛盾がないか

### 5.2 コード品質

- [ ] 不要なコメントアウト・`console.log`・デバッグコードが残っていないか
- [ ] 関数・コンポーネントが単一責任になっているか
- [ ] 重複コードがないか（あれば共通化を検討）

### 5.3 テスト・動作確認

- [ ] 主要な分岐（例：不足数0/1/複数）を手動またはテストコードで確認したか
- [ ] エッジケース（検索結果0件、未入力バリデーション等）を確認したか

### 5.4 ドキュメント更新

- [ ] 仕様変更があれば `recipe_app_spec_v2.md` の変更履歴（15章）を更新したか
- [ ] 破壊的変更があればREADMEやAPI仕様も更新したか
- [ ] 設計判断が伴う変更であればADR（7章参照）を追加したか

## 6. CI（継続的インテグレーション）

個人開発でも最初からCIを組み込み、「後で直す」を防ぐ。

### 6.1 PRごとに自動実行する項目

| 項目 | ツール例 |
|---|---|
| フロントエンドLint | ESLint |
| バックエンドLint | Laravel Pint |
| 型チェック | TypeScript (`tsc --noEmit`) |
| フロントエンドテスト | Vitest / Jest |
| バックエンドテスト | PHPUnit |

### 6.2 運用ルール

- CIが red の状態ではマージしない
- 将来的にCDを導入する場合は `main` マージ後に自動デプロイする構成を検討する（8章参照）

## 7. 設計判断の記録（ADR：Architecture Decision Record）

仕様書だけでは拾いきれない「なぜこの設計にしたか」という技術的な意思決定を、
`docs/adr/` 配下にファイルとして残す。チームに人が増えた際の引き継ぎ資料にもなる。

### 7.1 ファイル命名

```text
docs/adr/{連番4桁}-{内容}.md
例：docs/adr/0001-食材マスタ方式を採用.md
```

### 7.2 テンプレート例

```markdown
# 0001. 食材マスタ方式を採用

## ステータス
確定

## コンテキスト
食材の自由入力を許可すると表記ゆれにより不足材料の判定精度が落ちる懸念があった。

## 決定
MVPでは食材の登録・レシピ材料の入力ともに食材マスタからの選択のみとする。

## 影響
- 判定精度は担保されるが、マスタにない食材は登録できない
- 将来的に自由入力＋正規化への対応を検討する（spec_v2.md 12.1節参照）
```

## 8. 将来チーム開発へ移行する際の拡張ポイント

個人開発の間から以下を意識しておくと、人が増えたときにスムーズに移行できる。

- Issue・PRテンプレートは複数人での利用を前提とした文言にしておく
- レビューは「セルフレビュー」から「他者によるレビュー必須」に切り替えるだけで済む構成にする
- ブランチ保護ルール（PR必須・CI必須・レビュー必須）は個人開発中から `main` に設定しておく
- コミット・PRの粒度を小さく保つ習慣は、複数人開発でも重要になるため早期に定着させる
