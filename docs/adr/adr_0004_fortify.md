# 0004. 認証基盤としてLaravel Fortifyを採用

## ステータス

確定

## コンテキスト

`use_cases.md` UC-01（認証・アカウント管理）の実装にあたり、認証処理を以下のいずれかの
方法で実装するかを検討する必要があった。

- `AuthController` 等を自前で実装し、登録・ログイン・ログアウト・パスワードリセットの
  ロジックをすべて手書きする
- Laravel Fortifyを導入し、標準機能で大部分をカバーする

自前実装の場合、パスワードハッシュ化・ログイン試行回数制限（レート制限）・パスワード
リセットメールのスロットリング等、セキュリティに関わる部分まで自分で作り込む必要があり、
実装コストと不具合混入のリスクが高くなる懸念があった。

一方、本プロジェクトはReact（SPA）とLaravel（API）を`backend/` `frontend/`に分離した
構成（`adr_0003`参照）であり、認証はSanctum（Cookieベース）によるステートフル認証を
採用する方針としていた（10.4節・7.1〜7.3節）。Fortifyはビューを持たない「ヘッドレス」な
認証基盤であり、この構成と組み合わせやすい。

## 決定

認証基盤として**Laravel Fortify**を採用する。適用範囲は以下の通り分担する。

| 担当 | 対象UC | 実装方法 |
|---|---|---|
| Fortify | UC-01-01（ユーザー登録）、UC-01-02（ログイン）、UC-01-03（ログアウト）、UC-01-04（パスワードリセット・メール送信）、UC-01-05（パスワード再設定） | `app/Actions/Fortify/`配下のActionクラスをカスタマイズ（`naming_conventions.md` 2.7節） |
| 自前実装 | UC-01-06（退会・アカウント削除）、UC-02-01・UC-02-02（プロフィール表示・編集） | 通常の`Controller`クラス |

Fortifyの標準Actionクラス名（`CreateNewUser`、`ResetUserPassword`等）はそのまま使用し、
独自の命名には変更しない。

## 影響

- パスワードハッシュ化・レート制限・メールスロットリング等のセキュリティ実装をFortifyに
  委譲でき、自前実装に比べて実装コストと不具合リスクを下げられる
- SPA構成のため、Sanctumの`stateful`ドメイン設定とCSRF Cookie（`/sanctum/csrf-cookie`）
  取得をフロントエンド（Axios）側に実装する追加対応が必要になる
- コントローラー中心の命名規則（`naming_conventions.md` 2.2節）が認証部分には一部当てはまらず、
  Actionクラスという別の構成要素が増えるため、実装者はUC-01内でも「Fortify担当分」と
  「自前実装分」を意識して実装する必要がある
- プロフィール画像アップロード等、Fortifyの対象外機能は引き続き自前で設計・実装する
  必要がある（`recipe_app_spec_v2.md` 7.10節参照）
