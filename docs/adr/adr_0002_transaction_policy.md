# 0002. 複数テーブル更新処理のトランザクション方針を確定

## ステータス

確定

## コンテキスト

レシピアプリでは、以下のように複数テーブルにまたがる更新処理が存在する。

- 買い物リストの購入済みへの変更（`shopping_list_items` 更新 ＋ `user_ingredients` 追加）
- 不足材料の買い物リスト一括追加・重複食材の統合（`shopping_list_items` への複数件insert／統合）
- レシピ削除（`recipes` ＋ 関連する `recipe_ingredient`／`favorites`／`reviews`）
- 退会・アカウント削除（`users` 削除 ＋ `recipes` 匿名化 ＋ 個人データ削除）
- レシピ投稿（`recipes` ＋ `recipe_ingredient`）

これらは処理の途中で失敗すると、以下のようなデータ不整合が発生しうる。

- 購入済みにしたのに所持食材に反映されていない
- レシピ本体だけ削除され、お気に入り・レビュー等の関連データが孤児化する
- 退会処理が中断し、個人情報の一部が残存する

仕様書（`recipe_app_spec_v2.md`）にはこれまでトランザクション方針の記載がなかった。

## 決定

以下の処理はDBトランザクション（Laravelの `DB::transaction()`）で1つの原子的な操作として扱う。
途中でエラーが発生した場合は全体をロールバックする。対象となる処理・更新テーブル・理由の詳細は
`recipe_app_spec_v2.md` 10.4.1節の一覧表を参照（購入済みへの変更、不足材料の買い物リスト一括追加、
重複食材の統合、レシピ削除、退会・アカウント削除、レシピ投稿の6処理）。

また、以下の運用ルールを定める。

- トランザクション内では外部APIコール（画像アップロード等の外部I/O）を行わない。外部I/Oはトランザクションの前後で実施し、DB更新のみを原子的に扱う
- 単純な単一テーブル・単一レコードの更新（所持食材の削除、お気に入りの登録・解除等）はトランザクション必須としない

## 影響

- 上記処理の実装時は必ず `DB::transaction()` 等のトランザクション境界内にDB更新処理をまとめる必要がある
- 画像アップロードを伴う処理（レシピ投稿等）は、外部I/Oとトランザクション処理の順序・エラーハンドリング（例：画像アップロード成功後にDB書き込みが失敗した場合の孤児ファイルの扱い）を詳細設計時に別途検討する必要がある
- 具体的なロック戦略（悲観ロック／楽観ロック等の要否）は本ADRの対象外とし、詳細設計フェーズで別途決定する
